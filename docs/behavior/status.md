# Status: hooks, the transcript, background work

## Two sources

- With live status on, hooks say exactly what happened (`LiveStatus.apply`) and win over the transcript, except a stop: Claude sends no hook for Stop or Esc, so a transcript that ends in one after the last hook wins (`LiveStatus.holds`).
- Without hooks, status is guessed from the transcript's shape (`Recap.statusAndNext`).
- herdr's own reading of a pane counts between the two ([agents.md](agents.md)).

## Answering from the notch, per agent

- Claude's PermissionRequest hook runs alongside the app's own prompt, and whichever answers first wins, so Perch can allow, deny or answer a question (`answers` in `updatedInput`).
- A question's card ends with Other, the number after the agent's choices. It opens the card's reply field with the question above and the choices dimmed, and what you type is the answer (on a pick-several question, one more pick; a dropped file goes in as its path). Esc keeps the words on the row (app.js `otherRow`, `otherMenu`). The live activity's row has no Other.
- A question's choices are lit by one highlight that slides under the pointer (app.js `markChoice`), and each note is said in full. A question taller than the panel (four choices with long notes, and Other) scrolls its choices so its buttons stay on the card (`fitAsk`).
- In Bypass permissions mode Claude sends no PermissionRequest for a question, so Perch also installs a PreToolUse hook on `AskUserQuestion` (`Ask.viaPreToolUse`, tested against a real `claude` with a temporary settings file: allow plus `updatedInput.answers` is taken as the answer). That hook blocks the app's own prompt until it returns, so it is held only for a Claude app session you are not in, for the notch's nine seconds plus the question time, and let go the moment you are in that session (`HookServer.keepHolding`). `HookInstaller.upgrade()` adds it to an earlier install at launch.
- Codex's hook runs before its prompt, so Perch answers Codex at once with no decision and only shows the status.
- Perch's OpenCode plugin never blocks OpenCode: a permission or question is held open beside OpenCode's own prompt, an answer from the notch goes back through OpenCode's client, and one given in OpenCode makes the plugin drop its request.
- OpenCode runs other tools while a request waits on you, so a tool finishing does not settle an OpenCode request (`LiveStatus.apply`): only its answer does, here or in OpenCode, which lets the plugin's request go. A Claude tool run after a request still settles it.
- Cursor's hooks (`~/.cursor/hooks.json`, entries without a group around them) report `beforeSubmitPrompt` (started), `postToolUse` and `postToolUseFailure` (tool ran) and `stop` (completed, aborted or error); the chat's id is `conversation_id`, the same as the transcript's. Perch does not install the hooks that can allow or deny (`beforeShellExecution` and the like): they fire for every command, including ones Cursor runs without asking, so holding them would stall the agent, and answering them would replace Cursor's own prompt. Cursor also runs the Claude Code hooks in `~/.claude/settings.json`, so one turn can report twice, once as `claude` and once as `cursor`, with the chat's id as the session: harmless, they say the same thing.
- A Cursor approval is read from its database and answered in its window: the chat's header says `hasBlockingPendingActions` (written about 15 s after the prompt appears), and its newest tool call still `loading` says what is asked (`CursorStore.pending`: a command, a web search, a fetch, an edit). The card offers Allow and Deny (`Project.ask`, `Ask.answerable`); an answer needs the window to show that chat, then presses the prompt's button through Accessibility (`Run` or `Skip`, `CursorWindow.answer`). With Cursor running, the chat is chosen in the Agents window's own sidebar, so Cursor stays behind the app you are in, and the chat it showed before is chosen again afterwards; only when that fails, or Cursor is not running, does its link bring it forward and put you back where you were. A title does not identify a chat (two can share one), and the button is pressed in whichever chat the window shows, so nothing is pressed unless Cursor's own saved selection names the chat's id (`cursor/glass.selectedAgent` in the database, `CursorStore.selectedChat`) and the window's title agrees (`CursorWindow.confirmed`). The sidebar rows with the title are pressed in turn until the selection names the chat (`choose`); if none does, or the sidebar is hidden, the chat's link opens it by id. Cursor sets the pace: if its buttons are not on screen the answer reports Didn't send. A call waiting on you writes nothing to the transcript, so the chat's age is the later of the file's and the header's `lastUpdatedAt`; a request older than four hours is not offered. `beforeSubmitPrompt` must answer `{"continue":true}`, which the hook script prints itself, with or without Perch running (`HookInstaller.scriptBody`). Verified against Cursor 3.23.12 (payloads in [the spike](../spikes/cursor.md)).
- pi has no permission prompts. Its extension reports turns, tools, stops and extension prompts (pi 1.0+, answered in the terminal).

## A session no one runs

- A terminal session the scan finds no process for asks nothing: what its hooks said it asked settles (`LiveStatus.agentGone`), and a tool call its transcript leaves open reads as stopped mid-task, not at work or waiting for your OK (`Project.agentGone`). So a session killed while it waited stops holding the wings, and resuming it does not bring the old request back. A request held by its hook (OpenCode's) settles when that hook goes away instead.

## Background work

- A turn can end while work it left in the background is still out: helpers (the Agent tool run in the background), a watch (Monitor), a command run in the background or moved there when it ran long. Claude Code tells the agent with a task notification when each ends and the agent carries on, so until then the session is at work, not done, whatever the Stop hook said (`SessionDigest.background`, `Project.waiting`). The Now row says what it waits on (`Background.step`).
- The transcript has it all: the launch in the tool result's `toolUseResult` (`isAsync` and `agentId`, `backgroundTaskId`, a Monitor's `taskId`), the end in a `queue-operation` holding `<task-notification>` with a `<status>`. A watch's events have none, and a helper that stopped with work of its own still out says it "is waiting on its own background work" and reports again at the end.
- A command that never ends by itself (a dev server, `tail -f`) does not count (`Background.neverEnds`).
- Work gone without a word (the app quit) stops counting after half an hour with no sign of life (`Background.out`): a helper's sign is its own transcript, `<id>/subagents/agent-<agentId>.jsonl` (`SessionScanner.heardFrom`), a command's its start, a watch's its own deadline.
- Helpers send their hooks with the session's id and their own `agent_id`: a helper's tool call settles only what that helper asked, never the question the session itself asks (`LiveStatus.apply`).

## Trying it

- Test the socket without touching any config: `echo '{"session_id":"…","tool_name":"Bash","tool_input":{"command":"ls"}}' | ~/.config/perch/hook claude PermissionRequest` (it waits for your answer on the card).
- Post test questions this way, to an idle session: a message sent in a Claude session while its question is open dismisses the question.
